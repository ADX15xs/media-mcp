# 2026-08-05

## media-mcp: GitHub 发布工作流 + v0.1.0 prerelease

- 参考 `llm-eyes-mcp` 做法，新建 `.github/workflows/release.yml`：push tag `v*` 触发，matrix 构建 windows/amd64、linux/amd64、darwin/arm64，上传 artifact 后由 `softprops/action-gh-release@v2` 发 **prerelease**（含 sha256 校验和）。
- `main.go` 加了 `var version` 与 `--version` 输出，构建用 `-ldflags "-X main.version=${GITHUB_REF_NAME}"` 注入版本。
- 按用户要求**工作流与 tag 分两次推送**：先 push `main` 让 GitHub 注册 workflow，再单独 push tag 触发 release（避免一次性 push 不触发 Actions）。
- CI 首跑失败，根因排查：
  - 先把 `go.mod` 从 `1.26.3` 降到 `1.25.0`（对齐参考项目可用版本）——但**不是**根因。
  - 真正根因：`internal/mcp/transport_test.go` 的 `TestOnlyInitializeSendsNotification` 有 bug——用 `SetReadDeadline` 设 200ms 超时后读 pipe，无论读到数据还是超时都向 channel 发信号，把"超时"误判成"收到第二条消息"。Linux 上 `SetReadDeadline` 对 pipe 生效（200ms 触发超时）故失败；Windows 上该调用静默失败、Read 阻塞反而"碰巧"通过。修复：仅当 `n>0`（真正读到字节）才算收到消息。
  - 诊断手段：因 GitHub API 日志需 token，临时让失败 job 把 `go test` 输出推到公开分支 `ci-debug`，用 `raw.githubusercontent.com` 免鉴权读取，定位到具体失败测试；修复后已删除该分支与诊断逻辑。
- 最终结果：release 工作流 SUCCESS，`v0.1.0` prerelease 已发布，含三平台二进制 + checksums.txt。
- 历史清理（用户"开始处理历史遗留"）：`git reset --soft 50de90f` 把 5 个发布/调试 commit 压成单个 `1a8b3b1`（"ci: add release workflow and v0.1.0 prerelease setup"），`git push --force origin main`。当时 `v0.1.0` tag 仍指向原 release commit `41d950e`（树与 1a8b3b1 完全相同，release 产物有效）。
- 标签对齐（用户"执行对齐"）：`git tag -f v0.1.0 1a8b3b1` 后 `git push -f origin v0.1.0`，远端 tag 现指向 1a8b3b1。release 的 `target_commitish=main`，tag 解析到的 commit 即 main HEAD，故 release 自然跟随；`git describe --tags` 从 HEAD 返回 `v0.1.0`，4 个资产完好。
- 结论：main HEAD == tag v0.1.0 == 1a8b3b1，历史清爽且发布完整一致。后续新发布直接打新 tag 即可，无需再动历史。
