## 排查：WorkBuddy 调用 media-mcp 两次都 -32001 Request timed out

**根因**：media-mcp 的 `tools/call` 是完全同步阻塞的——`transport.go:71` 虽用 goroutine 处理，但 goroutine 内一直阻塞到 `GenImage/GenVideo` 返回才回包。而 WorkBuddy 的 MCP 客户端对单次请求有较短超时（MCP SDK 默认 ~60s 量级），超时即抛 `-32001` 放弃，服务端其实仍在后台跑。

**耗时数据**（grep 证据）：
- 视频：`agnes_video.go` create 60s / poll 30s，但 `pollTask` 整体 `totalTimeout=15min`（:52），即一次 generateVideo 最多 15 分钟才回包。
- 图像：agnes_ai 300s(:163)、doubao 360s(:158)、sensenova 180s(:76)，单图请求本身 3–6 分钟。
- 兜底 `http_generic.go:80` `http.Client{}` 无 Timeout，上游卡住会无限挂。
- 全仓库无 server 级 / 客户端侧 requestTimeout 配置。

**结论**：MCP 长任务 vs 短请求超时的经典错配；server 未用 progress 通知，也未采用「先返 task_id 再轮询」非阻塞模式（而 agnes_video 其实已支持 `task_id`/`video_id` 重连，地基具备）。

**修复方向（未实施，待用户确认）**：① 视频工具改非阻塞——创建即返回 task_id；② 兜底补 Timeout；③ 处理期间发 `notifications/progress`；④ 客户端超时调到 ≥15min（文档未暴露该配置）。

## 补充：行业超时 / 2026-07-28 规范定调

- **行业常见 MCP 请求超时**：无强制标准，由客户端/传输层定。TS/Python SDK 历史默认 60s；SpringAI Streamable HTTP 默认 20s；通用 HTTP 环境 30s–2min。结论：都是秒级~一两分钟，绝不会到 15min → 阻塞式长调用必然 -32001。
- **2026-07-28 spec（最新）**：去掉持久会话（无状态化），`Tasks` 扩展（`io.modelcontextprotocol/tasks`）提为头等。范式就是非阻塞返回持久 `taskId` + `tasks/get` 轮询。这**不是延长客户端超时的开关**，而是逼你改成「句柄+查询」模式——与无状态方向一致。
- **关键约束（已修正）**：Tasks 是 2025-11-25 起实验、2026-07-28 提为第一类的真实 MCP 原语（SEP-1686，TS/Python SDK 参考实现随规范发布，与"多数厂商 Day 0 适配"一致）。但**WorkBuddy 客户端是否实现 Tasks 尚未核实**，此前"大概率未实现"属无据推断，已纠正。不论是否支持，media-mcp 服务端必须停止阻塞 tools/call（当前既未声明 capabilities.tasks、也未返回 CreateTaskResult，故即使客户端支持 Tasks 现在也不会进入任务模式）。stdio 下 `notifications/progress` 多数 SDK 不重置 requestTimeout，不能靠它救火。
- **落地结论**：现在就在 stdio 上实现「Tasks 形态的手动版」——两段式工具（submit 返 task_id + get_result 轮询）+ 可选 progress 透传 task_id。transport-agnostic，今天客户端可用；未来 WorkBuddy 支持 Tasks 后机械收敛为原生 CreateTaskResult。图像因上游同步（3–6min）本质受客户端超时限制，只能把 adapter HTTP Timeout 设到略低于客户端超时以拿到干净错误，或换异步供应商。
