## agnes_video "task not found" 事故排查与修复

**现象**：连续 3 次调用 `agnes_video_generateVideo` 报 `task <id> not found`，但 Agnes 后台 3 条记录全部生成成功。
涉及 task_id：`task_kw09iqem1bnofXwU5MVqbqU3cl8BAj9Q` / `task_CgRqN52KTlYxJFHnMSG2tnvi9iICmCaX` / `task_2VsmGTevQq1bSrptPBLnqnJROaRrhiea`（11:12–11:15 提交）。

**结果**：3 个视频已全部捞回至 `test-media-generations/artifacts/recovered/`。

### Agnes 视频 API 实测结论（重要，写入 images-generations/Agnes.md）

- `agnesapi?video_id=<VIDEO_ID>` 是**唯一**返回成品 `url` 的端点，进度更新更快。
- `/v1/videos/<TASK_ID>` **从不返回 url**，但会返回 `video_id`，可据此转查 agnesapi；状态更新滞后于 agnesapi。
- `/v1/videos/<TASK_ID>/content` 恒返回 `{"detail":"Not Found"}`（HTTP 200 + video/mp4 头），不可用。
- **创建接口有限流**：连发 3 个任务，第 2、3 个直接 429 → 视频任务必须串行提交。
- **状态接口限流激进**：4 路并发轮询约 29% 命中 `429 video status query rate limit exceeded`。
- 状态接口会**间歇性返回 404 `{"error":{"code":404,"message":"task not found"}}`**，但任务照常跑完。
- `seconds` 是字符串（`"5.0"`）；`frame_rate` 在 `request_params` 内，顶层没有。
- `video_id` 是 base64 LiteLLM 路由令牌；任务完成后其中的 `model_id` 会被重写为空值（排查时是红鲱鱼，不代表异常）。

### 根因

`agnes_video.go` 的 `pollTask` 把 HTTP 404 当作**终态**直接 return，一次瞬时 404 就丢弃了服务端仍在跑且最终成功的任务；且错误里不带 task_id/video_id，无法找回。轮询期间零日志，事后无法诊断。

### 修复（已验证）

1. 404/429/5xx/网络错误一律视为瞬时错误 → 双端点回退重试，3 分钟宽限期内不放弃。
2. 放弃任务时 `abandon()` 必定打印 task_id/video_id + 找回 curl，错误消息里也带上。
3. 提交成功后立刻无条件 log `task_id` / `video_id`（唯一的找回抓手）。
4. 新增**任务重连**：`*_generateVideo` 支持 `task_id` / `video_id` 入参，跳过创建直接取回结果，不重复计费。
5. 修正字段解析：`id`/`status`/`internal_status` 回退、`seconds` 字符串转数字、`frame_rate` 从 `request_params` 取（此前 Duration/FrameRate 恒为 0）。
6. 从 `/v1/videos/<task_id>` 自动发现 video_id，再转 agnesapi 取 url。
7. 新增 `internal/supplier/log.go`：`logf` / `debugf`，`MEDIA_MCP_DEBUG=1` 打完整请求/响应体。
8. 轮询时序抽成 `pollTiming` 结构体，可经 config `extra` 调整，测试用压缩时序。
9. 同样的 404 容错补到 `http_generic_video.go`。

新增 `internal/supplier/agnes_video_test.go`（含 404→429→completed 的回归测试）。全量 `go test ./...` 通过。

## 评审：agnes-video-tool-optimization-spec.md（视频尺寸控制优化规格书）

评审结论：**方向正确但不可直接交付**。产出 `docs/agnes-video-tool-optimization-spec-review.md`（9 条问题清单）。

关键发现（对照代码核实）：
- 规格书 §2 的 schema 快照与代码不符：实际 schema 含 `task_id`/`video_id`；`additionalProperties: false` 在 transport.go 中不存在（透传被阻的真实机制是 handleToolCall 白名单提取丢弃未知字段）。
- **1088×832 不是"上游默认"**：adapter 始终请求 1152×768（agnes_video.go L58-59），该输出证明**上游不精确遵循 width/height**（与图像侧 1024x768→1152x864 归一化行为一致）→ 方案 B 映射表（传 1080×1920 得 1080×1920）前提被自己数据否定。
- 本 server 手写 JSON-RPC 无 schema 校验，"MCP 层 enum 强校验"不存在，需自实现。
- `negative_prompt` 在 Agnes.md 视频文档中无此字段，未验证不应进 schema。
- 规格书调研外部厂商却漏掉仓库内 Agnes.md 既有断言（视频支持 480p/720p/1080p + 9:16 等 5 比例，同样未实测）。
- 最小实现路径很短：`VideoRequest.Extra` 覆盖机制已存在（agnes_video.go L156-158 可覆盖 payload 的 width/height），transport 透传 + adapter 查表即可。

后续建议：先做探针实验（直接传 9:16/16:9/1:1 尺寸调上游，ffprobe 实测输出，得"请求→实际"事实表），再定暴露面与映射表。

### 规格书 v2.0 修订

用户确认设计决策：**不暴露 agnes 原始 width/height，暴露 `aspect_ratio` + `resolution` 枚举**（行业 schema 对齐，方便 Agent 客户端调用）。按评审结论修订产出 `docs/agnes-video-tool-optimization-spec-v2.md`：修正 schema 快照（含 task_id/video_id）、1088×832 定性（上游对 1152×768 的响应）、新增阶段 0 探针实验（用例 0a–0f，前置必做）、negative_prompt 移出 v1、enum 校验改为 wrapper 自实现（本 server 无 schema 校验引擎）、实现落点明确为 transport 透传 + adapter GenVideo 查表覆盖 req.Extra。

## 代码审查：图像生成（image generate）抽象层拓展性

用户要求顺带检查图像侧。`go test ./...` 当前仍全绿（问题不在测试，在架构/可达性）。

**核心结论：图像侧抽象比视频侧更脆弱——真实能力被塞进 `Extra`，transport 既不在 schema 暴露也不转发未知参数，导致 agent 用不了；且与视频侧（第一等字段 + 共享 helper）形成不一致。**

发现（均 file:line 已核实）：
1. **`ImageRequest.NegativePrompt` 是死字段**：transport.go:216 写入，但三个图像 adapter 无一读取——agnes_ai/senseNova 忽略；doubao 只读 `req.Extra["negative_prompt"]`（doubao_seedream.go:116）而非结构体字段。结果：工具参数 `negative_prompt` 对所有图像 provider 完全无效。
2. **`ImageRequest.Style` 在图像侧是死字段**：transport 图像 handler 从不设置它（图像 schema 无 style 参数），无图像 adapter 读取；仅视频侧在用（agnes_video.go:174、http_generic_video.go:100）。图像/视频不对称。
3. **provider 能力困在 `Extra`、MCP 不可达**：agnes 的 `ratio`/img2img（agnes_ai.go:96,112）、doubao 的 `negative_prompt`/`image`/`max_images`/`stream`/`optimize_mode`/`web_search`（doubao_seedream.go:102-151）全部从 `req.Extra` 读取；但 transport 图像 handler 不转发未知参数，也不 populate 图像 Extra → 这些功能经 MCP 工具**完全无法使用**。`Capabilities()` 只是 description 文本提示，无法补 schema 参数。
4. **通用兜底低估 schema**：`HTTPGenericAdapter.GenImage` 只发 prompt/model/size/n（+ExtraFields+req.Extra），忽略第一等 `negative_prompt`/`style`。零代码接入 provider 拿到承诺了 negative_prompt 的 schema 却实现不了。
5. **缺 schema 扩展钩子**：视频侧已用第一等字段 + `supplier.SizeTable`；图像侧仍靠 `Extra` + 各 adapter 手写解析。新增图像 provider 要暴露常见能力（negative_prompt/ratio）只能埋进 Extra（不可达）或改 transport+schema（摩擦）。无 `CapabilityProvider` 风格的"声明额外 inputSchema 参数"接口。

**建议方向（待用户确认是否实施）**：对齐视频侧——把 `negative_prompt` 真正消费掉（adapter 读 `req.NegativePrompt`）；引入 `SchemaExtender` 接口让 provider 声明自有 inputSchema 属性，transport 合并进各工具 schema（替代纯文本的 `Capabilities()`）；`ratio` 之类若通用可升为第一等字段 + 共享 helper。
